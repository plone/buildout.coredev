Fix TypeErrors (HTTP 500) from request parameters in search/summary serialization (#2060)

Two code paths in the REST API search and summary serialization could raise a
TypeError (returned as HTTP 500) based on request input:

1. DefaultJSONSummarySerializer stored the merged serializer metadata on the
   request with request.set() (which writes to request.other), but read it back
   with request.form.get(). The cached value was therefore never found, so the
   metadata was recomputed for every serialized item, for example once per
   search result. In addition, a client-supplied form or query string parameter
   named summary_serializer_metadata made metadata a string and raised a
   TypeError when it was indexed as a dict. Read the cache back with
   request.get() so it is reused, and guard it with isinstance(metadata, dict).

2. SearchHandler.filter_query() checked "query" in types to detect a
   {"query": ...} portal_type dict. For a string portal_type this is a substring
   check, so a value containing "query" (for example "Subquery") was indexed as
   a dict and raised a TypeError. Guard the check with isinstance(types, dict).

Add regression tests for all three cases; each fails without the fix.
