Return the error when a TUS upload fails to create content (#2076)

* Return the error when a TUS upload fails to create content

UploadPatch.reply ignored the return value of create_or_modify_content
and fell through to reply_no_content, which reset the status to 204 and
dropped the error body. A failed final PATCH therefore looked like a
successful upload.

reply now returns the error when create_or_modify_content reports one.
Successful uploads still get 204 with a Location header.

Tests cover a type without a primary field and no fieldname (400, nothing
created) and a type with a primary field (204 with Location).

Refs #2075

* Handle a missing primary field when resolving the TUS upload field

plone.dexterity 2.x raises TypeError from the IPrimaryFieldInfo adapter
when a type has no primary field, instead of returning None. The
default argument to the adapter lookup does not cover that, so on
Plone 5.2 a final @tus-upload PATCH for such a type (for example
Folder without a fieldname) answered 500 instead of 400 Fieldname
required.

Catch the TypeError the same way the DX serializer already does.
